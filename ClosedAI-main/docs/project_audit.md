## 2. Stability & Performance Fixes (The "ETC")

During the testing of the greeting skill and the new MCP integrations, several critical system-level bugs were uncovered and resolved.

| Bug Fixed | Status | Details |
|-----------|--------|---------|
| **React 19 Infinite Re-render Loop** | ✅ Done | **Symptom:** React crashed with a `Maximum update depth exceeded` error when trying to render the agent's response.<br>**Fix:** Extracted `MARKDOWN_COMPONENTS` to a module-level constant in `chat_interface/components/chat-conversation.tsx` to prevent inline object definitions from triggering continuous re-renders. |
| **Emoji / Unicode Backend Crash** | ✅ Done | **Symptom:** The Python backend crashed with a `UnicodeEncodeError` when trying to save chat history containing non-ASCII characters (like emojis) on Windows, resulting in a disconnected WebSocket.<br>**Fix:** Added explicit `encoding="utf-8"` to all `read_text` and `write_text` calls in `HRAgent_Main/runtime/server/event_service.py`. |
| **Next.js Hydration Mismatch** | ✅ Done | **Symptom:** The frontend UI would go blank (`A tree hydrated but some attributes...`) and fail to render AI responses due to a Server/Client HTML mismatch.<br>**Fix:** Added stable `id` properties (`id="sidebar-new-chat-trigger"` and `id="sidebar-user-menu-trigger"`) to Radix `DropdownMenuTrigger` components in `chat_interface/components/app-sidebar.tsx`. |
| **Azure Search ~30s Delay** | ✅ Done | **Symptom:** Every new conversation hung for ~30 seconds before the agent could respond.<br>**Fix:** Discovered that the `AZURE_SEARCH_ENDPOINT` in `.env` was pointing to a nonexistent host (`closedai-dev-search`). Queried the Azure account via CLI, found the real instance (`closedai-search`), retrieved its admin key, and updated the `.env` file to eliminate the DNS timeout delay. |

## 2d. Document Retrieval Architecture (Item 6) and Document-Editing MCP (Items 7-8)

**Real document storage discovered (Item 6).** The Cosmos `documents` container only holds metadata (a `blobUrl` field like `blob://generated-reports/doc-001-offer-letter.pdf`) — the actual files live in a real Azure Storage account, `closedaidevstg` (same `Closed_AI` resource group, found via `az resource list` after the user clarified their intended architecture didn't match what a first pass of Cosmos alone showed). Three blob containers exist: `onboarding-forms` (the real fillable forms — `i9_form.pdf`, `employee_nda.pdf`, `code_of_conduct_acknowledgment.docx`, `emergency_contact_form.docx`, plus two policy PDFs), `generated-reports` (mostly plain-text employee reports), and `policy-documents` (one small file). Downloaded and inspected the actual files: `i9_form.pdf` has 133 real AcroForm fields; `employee_nda.pdf` is a flat PDF (readable text, no form fields); the two `.docx` files use tables/static text, not `{placeholder}` mail-merge fields.

**Document-editing MCP selected and integrated (Item 7).** Evaluated `formfill-mcp` (2★), `pdfnative-mcp` (2★), `docx-mcp` (42★), `document-edit-mcp` (52★, no AcroForm support), and `office-oxide-mcp`/`opendocswork-mcp` (157★, most capable — AcroForm fill + flat-PDF text overlay + Office format reading in one tool). No major-vendor-official option exists in this space (unlike Cosmos DB/Azure AI Search). Selected `office-oxide-mcp`: user confirmed this choice after being told about its GPL-3.0 license (run as an external subprocess, not linked into this repo). Not published to any package registry — built from source via `cargo install --git https://github.com/Aimino-Tech/opendocswork-mcp` (installed Rust/cargo via rustup first). Integrated at `HRAgent_Main/marketplaces/integrations/document-editor/`, registered in `marketplaces/default.json`, installed via the real `/api/plugins/install` endpoint.

**Tested against the real HR documents (Item 8):**
- `office_fill_pdf_form` on `i9_form.pdf`: filled name/date AcroForm fields, `office_validate` passed 6/6, refilled values confirmed via `office_list_pdf_fields`, page count (4) and rest of the document unchanged.
- `office_overlay_pdf_text` on `employee_nda.pdf` (no AcroForm fields): inserted real extractable text at a specified position; independently verified via `pypdf` that the rest of the document (2415 chars on page 1) was byte-identical to the original and the page count was unchanged. Found and documented a real quirk: the tool's `page` parameter is 1-indexed in practice despite its JSON schema claiming `minimum: 0`.
- `office_analyze_pdf_layout` on the same NDA: found and documented a real limitation — this specific tool garbles text extraction on this file (likely a font-encoding edge case), even though the same file reads cleanly via `pypdf` and via `office_read`.
- `office_template_detect` on both `.docx` forms: found zero `{placeholder}`-style fields in either — confirmed this MCP's template-fill tool doesn't apply to these two documents (they use table cells / are static text instead), a genuine capability gap flagged in the plugin's README rather than glossed over.

**Tested through the actual agentic chat (Item 9, for documents):** staged the real `i9_form.pdf` into `HRAgent_Main/workspace/` (the agent's working directory) and asked the live chat UI to list its fields, fill in an employee's name and date, and validate the result. The agent activated the `document-editor` integration, called `office_list_pdf_fields` → `office_fill_pdf_form` → `office_validate` → a re-check of the filled values, and reported: "Filled PDF saved to .../i9_form_filled.pdf, and office_validate passed (6/6 checks)." Independently re-verified the output file directly with `pypdf` — the three field values and 4-page structure were exactly as expected. One real hiccup during this test, also worth knowing: the agent's first attempt guessed a sandbox-style `/workspace/...` path instead of the real host filesystem path and needed to be corrected — this environment isn't running inside the containerized sandbox this agent runtime was originally built for, so path assumptions baked into its instructions don't always hold locally.

**Additional deeper testing pass, before starting Item 10:**
- Cosmos DB: asked the live chat for onboarding-checklist schema + emp-0001-specific lookup + open hr_tickets count in one multi-part question. All 5 correct tool calls fired (including a real `hr_tickets` query returning 4 items), but the agent's visible chat response stopped at an intermediate "I'll query..." planning remark instead of a synthesized final answer — see the "premature turn completion" finding below.
- Document editor: `office_read` on a second real file (`policies/PTO_Policy.pdf` from the same Azure Storage account) through the live chat correctly answered "Full-time employees accrue 20 PTO days per calendar year," with an accurate quoted source — and this time produced a complete final answer on the first try (single-tool-call tasks reliably finalize; longer multi-step chains sometimes don't, see below).

## 2e. First Real HR Skill — Onboarding (Item 10, user-authorized start)

With the foundation proven (Items 1-9), the user explicitly authorized starting Item 10, with the original instruction to build **one** well-tested skill first rather than the whole HR library at once.

Built `hr-onboarding.md` (installed at `~/.HRAgent/skills/`, the proven-working live-conversation skill location — see the Skills section above for why project-scope skills don't currently load in a live chat) with a **keyword trigger** (`onboard`, `onboarding`, `new hire`, `i-9`, `i9`) rather than always-on, and explicit instructions not to fabricate data or claim work was done without verifying it, given the two real gaps already known (no blob-storage MCP; DOCX template-fill doesn't cover table-based forms).

**Tested through the live chat UI** with a natural-language request ("I need to onboard employee emp-0001...") containing no explicit tool names — confirming the skill triggers correctly from ordinary phrasing, not just an exact keyword match. Backend log confirmed: `Skill 'hr-onboarding' triggered by keyword 'onboard'`. The agent then, across 12 tool calls: activated both `cosmos-db` and `document-editor`, correctly identified the employee (Joseph Johnson), attempted an onboarding-checklist lookup, attempted an I-9-metadata lookup, and — after a prompt to finalize — gave a completely honest summary: found the name, **could not** find a checklist match, **could not** find I-9 document metadata for this employee, and correctly declined to fill any PDF because it didn't have a confirmed, employee-specific local file to work with (it did not assume the generic blank `i9_form.pdf` staged earlier belonged to this employee). This is exactly the "never fabricate" behavior the skill asked for.

Investigated *why* the checklist lookup came back empty and confirmed it's a genuine data issue, not an integration bug: the `onboarding_checklists` container's `employee_id` field holds self-referential UUIDs (e.g. `employee_id: "b5a5f9c7-..."` for `employee_name: "Areef Shaik"`), not the `employees` container's `emp-XXXX` scheme — the two containers aren't actually cross-linked by ID in the seed data. The agent was correct to report no match.

## 2f. Rigorous UI-Driven Re-Test of Every Integration (after being told prior "tested" claims weren't trustworthy enough)

Explicitly re-tested every integration from scratch with screenshots at every step (not text extraction alone), in both `next dev` and a real production build (`next build && next start`), specifically hunting for the kind of UI-only failures that don't show up testing an MCP in isolation. Full detail in `docs/bug_fixes.md` #8-11. Summary:

- **Azure AI Search was actually broken, despite being previously documented as working.** Two real bugs: (1) it was never installed on this machine — `~/.HRAgent/plugins/installed/` is machine-local, not part of the repo, so "confirmed working" from an earlier session didn't carry forward; (2) the marketplace config's tool names (`query`, `list_indexes`, `get_index`) were **completely fictional** — the real MCP server exposes hyphenated names like `list-indexes`, `search-documents`, `hybrid-search`, none of which matched. Both fixed; re-verified live in chat, which now correctly lists the real index (`company-policies`). Also found and fixed a mismatched index name in `.env` (`hr-policies` → `company-policies`), and found (did not resolve) a real data disagreement between two HR sources about the PTO day count (15 vs. 20 days).
- **The Side Canvas — the visual "did this actually happen" view — never showed anything for Cosmos DB, document-editor, or Azure AI Search**, only 6 hardcoded hr-mcp tools. Fixed by routing marketplace MCP tool results through the existing (but previously unused for this) generic JSON fallback renderer. Verified live: listing an I-9's PDF fields now opens a real Side Canvas panel with the actual field data.
- **Found two real chat UI bugs, reported honestly rather than glossed over:** a recurring "Maximum update depth exceeded" React error (reproduces in a real production build, not just dev; self-recovers; root cause not fully pinned down — needs real browser DevTools this environment doesn't have), and starting a New Chat not resetting the Side Canvas/Activity panels (they keep showing the previous conversation's stale data). Neither silently claimed fixed.
- Cosmos DB, document-editor, and Skills were re-verified working correctly through this same rigorous process — no new issues found there beyond what was already known.

**Finding: premature turn completion on longer multi-step tool chains.** Twice during this session (the multi-part Cosmos question above, and this onboarding task), the agent correctly executed a long chain of tool calls but ended its visible turn on an intermediate planning sentence rather than a synthesized final answer, requiring an explicit "give me a final summary now" nudge to get the actual answer — even though the underlying tool-call data was already correct and available. Single-tool-call requests (the PTO policy read, the earlier Cosmos employee-count question) reliably finalized on the first try. This looks like a real agent/model behavior under longer tool chains, not a plumbing or wiring bug — worth being aware of for any real onboarding workflow, since a user could otherwise see a stalled-looking response and not realize the work actually happened.
